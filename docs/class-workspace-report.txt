Classes and sections workspace — 2026-10-19

Scope
Approved changes to the class settings workspace only. General profile/timing implementation,
student directory routes, auth and platform administration were retained. Both repositories
already contained extensive uncommitted work; no reset, clean or commit was performed.

Behavior
- Visible settings label is Classes & sections. Existing bookmarked tab URLs remain valid.
- One class selector and summary above Sections / Students / Subjects; structural controls
  appear only under Sections. A section's student count opens its filtered roster directly.
- Set up classes creates several classes with their sections in one operation. Paste one class
  name per line, apply comma-separated section names, and adjust each row before saving.
  Supports 1–50 classes, 1–20 sections per class, maximum 200 sections per request.
- Class means the learning level; section means a group within that class. Existing names
  such as Grade 5 are retained as data. Existing optional grade metadata remains available
  under Curriculum level in the edit dialog; it is not another required creation step.
- Excel import stays inside the selected class: existing demo preview dialog, existing live
  durable import-job workflow. Existing workbook columns, corrections and validation retained.
  Live import resumes after refresh and updates class counts on return to the roster.
- Original subject defaults and subject editor retained, with the common class selector above.
- Demo uses local repository persistence. Live uses authenticated scoped APIs only.

Backend dependency
POST /api/v1/schools/:schoolId/academic-years/:yearId/classes/setup
Body: { rows: [{ name, sections: [name, ...] }], includeDefaultSubjects?: boolean }
Response data: { saved: number }
Uses existing academic collections, schoolWrite transaction/permission recheck, CSRF,
unique indexes and audit events (classes.setup). Requires classes.manage + sections.manage;
subject provisioning additionally requires subjects.manage. Closed years are read-only.
Class setup is atomic; a later conflict rolls back earlier classes, sections, subjects and audit.
Student imports retain their existing durable per-row processing semantics, not batch atomicity.
No migration, new environment variable, dependency or lockfile change required.
