## Safety and upgrade approach

No remote data changes, credentials, environment edits, dependency changes, or destructive migrations. New optional profile/identity fields require no destructive rewrite. Any new indexes/catalog backfills use an explicit versioned command. Catalog provisioning is an authorized explicit write, never a GET or startup side effect. Existing queued import jobs keep their original format. A real deployment still needs operator verification, backups and production load/security review.

## Implemented product flow

This report supersedes the separate live wizard flow described in the earlier onboarding report. Owners enter **Settings → General**, using the same School Profile and School Timing presentation as demo mode. School name, motto, location, board, affiliation, principal, contact details, website and logo persist through the existing revision-checked profile API. The additional existing live address, state/region, country, postal code, timezone and accent fields remain available in that same form. Registration code remains platform-managed. Optional timing can stay unconfigured; partially entered timing is rejected. Raster branding is bounded and validated; SVG and remote image URLs are rejected.

**Academic years** remain an explicit prerequisite for academic data. Create a draft, then select it as current. **Classes, Sections & Grades** preserves the actual **Sections / Students / Subjects** tabs. The shared class/section dialog, class selector, section teacher display, student counts and subject editor are reused. Bulk class and section configuration is integrated into this area, along with bulk subject editing and archive restoration. Changes require review before committing. Closed years and truncated bulk snapshots disable editing; reference guards preserve enrollment and assignment history.

New classes created through the live screen atomically receive their grade/board defaults when the operator also has `subjects.manage`. Existing classes offer an explicit “Apply class subject defaults” action. Classes managed by users without that grant require a subject manager to initialize subjects. Catalog version `schoolwell-demo-subjects-v1` copies the rules in `src/lib/classSubjects.ts`, including the original nonnumeric-grade fallback and ICSE/ISC split. The old generic catalog was replaced because it did not match the product. These are product defaults, not a certification of any board syllabus. Synthetic demo examination records are not copied into live schools.

Each subject is a school/year/class-owned record with a stable ID, optional flag, status, revision and optional source catalog/key. A class records its initialization version. Reapplying defaults returns zero new records after initialization; renames, optional flags and archived subjects remain unchanged. Future catalog upgrades need explicit reconciliation, not resetting existing classes. Previously created custom subjects with matching names are retained when a class is first initialized.

The **Students** directory and the Students class-settings tab read real enrollments. Search, class/section filters, bounded pagination, individual admission, profile/guardian details, revision-checked edits and withdrawal use school-scoped APIs. Admission number identifies the student within a school; enrollment is unique per student and academic year. Names and guardian phone numbers do not identify students. Admission number, class, section and roll cannot be silently changed through profile edits/imports. Withdrawal preserves identity and history; transfer/reactivation needs a separate future workflow. Live admission numbers currently use the existing backend limit of 40 characters, shown in the form and import errors.

The live download calls the **same generated workbook** as demo mode: `Students` and `Instructions` sheets, with the original nine columns and order. Existing test workbooks are fixtures, not alternative product templates. The current generator has no example rows, dropdowns or cell validation to preserve. The selected class is persisted in the import job; the Section cell chooses an active section in that class. Relationship defaults to Parent. DOB, guardian, admission and roll fields retain their required semantics. File parsing rejects formulas, invalid headers and oversized/invalid workbooks; the server independently validates rows and persisted references.

The existing durable import worker handles both the new `demo-students-v1` format and previously saved `legacy-v1` jobs. Preview does not create people. Corrections are revision checked, followed by validation before confirmation. Each committed row atomically saves its profile/enrollment and outcome. Content fingerprints make repeated submissions return the existing job; identical existing people are skipped. Update mode is explicit and requires a preview revision; it replaces supplied profile fields, including clearing optional values. Outcomes report actual created/updated/skipped/failed counts. Partial failures remain visible and retryable. Exports guard spreadsheet formula injection. A controlled-error prototype regression found by legacy tests was fixed so row problems stay in preview instead of pausing the whole job.

**Teachers** and **Staff & HR** provide real directories, individual profiles, bounded raster photographs, CSV/XLSX bulk imports, archive/restore and teaching assignments. The shared contact fields and familiar profile controls are reused. Assignments validate active same-school staff and year/class/section/subject references. Class teachers also require active teaching staff; restoring a section revalidates a retained teacher. Staff imports/profiles never create users, passwords or memberships. Payroll, staff work-rule configuration and salary history require a dedicated future payroll implementation; their demo screens remain intact and live screens explicitly state the limitation.

The live sidebar exposes supported, permitted Overview, Students, Teachers, Staff & HR and Settings routes. Settings groups use the demo terminology. Account/role/member/audit operations remain available under their corresponding groups; older tab aliases resolve into the new groups. The previous `SchoolSetup`, `ProfileEditor`, `AcademicStructure` and `StructureEditor` source files are retained as unmounted legacy implementations, preserving pre-existing user work. They are no longer competing live entry points. No useful database data or existing demo screen was deleted.

## Persistence, API and security contract

All paths below are relative to `/api/v1/schools/:schoolId`. Existing authentication, CSRF, school membership and server-defined permissions apply. Super Admin status alone does not confer tenant operational access.

| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET/PATCH /profile`                                                    | `school.profile.view/manage`; bounded approved fields, revision check, audit; optional raster logo and nullable hours                              |
| Existing academic-year endpoints                                        | `academic-years.view/manage`; draft/current/closed lifecycle retained                                                                              |
| `GET /academic-years/:yearId/structure?kind=…`                          | Resource `.view` plus `classes.view` and `academic-years.view`; bounded snapshot                                                                   |
| `POST /academic-years/:yearId/structure-batch`                          | Resource `.manage`; transactional batch, revisions and references; `includeDefaultSubjects` additionally requires `subjects.manage`                |
| `POST /academic-years/:yearId/classes/:classId/subject-defaults`        | `subjects.manage`; explicit, idempotent school-owned copies and audit                                                                              |
| `GET /academic-years/:yearId/student-context`                           | `students.view`; scoped class/section choices without staff IDs; does not require a student clerk to read staff profiles                           |
| `GET /academic-years/:yearId/student-roster`                            | `students.view`; filters `classId`, `sectionId`, `search`, `studentId`, `after`; maximum 50 rows, total and cursor; approved nested student fields |
| `GET /academic-years/:yearId/student-counts`                            | `students.view`; derived active enrollment counts, never client-supplied                                                                           |

| `POST /people/staff`, `PATCH /people/staff/:id/details`                 | `staff.manage`; existing nine staff fields, optional validated `photoDataUrl`, revisions on edits                                                  |
| Existing `/people/:kind`, status and relationship endpoints             | Existing view/manage grants; staff directory supports `teaching=true`; archived/reference guards retained                                          |
| Existing `/imports` preview/detail/correct/confirm/retry/cancel/results | Kind-specific manage grant; student product format additionally carries `format` and `classId`; the worker rechecks access/year state              |

No new collections or indexes were necessary for this extension. Existing collections and indexes remain authoritative:

- Schools: profile revision, academic revision/current-year pointer; add optional logo data.
- Academic classes/sections/subjects: school + year + normalized name uniqueness (children also class-scoped), stable IDs, status/revision and bounded snapshot indexes. Add optional class catalog marker, section teacher ID and subject source metadata.
- Student identities/staff profiles: unique school + normalized admission/staff code and school + ID paging. Add guardian relationship (Parent fallback) and optional staff photo.
- Enrollments: unique school + year + student and school + year + section + roll; year paging/class-status indexes. Student identity survives across years.
- Assignments: scoped uniqueness on year/staff/section/subject; scoped paging/reference indexes.
- Import jobs: existing scoped fingerprint uniqueness, durable row status/revisions and lease recovery indexes. Add optional format/class context; old jobs retain legacy interpretation.

Writes use the existing school lock/transaction boundary and audit service. Reads and joins are tenant-scoped; ObjectIds and query fields are validated. Foreign references return controlled errors. API responses never expose raw database errors, credential fields, session secrets or arbitrary exception text. Client caches remain memory-only and invalidate on writes/authentication changes. School and route context remounts prevent stale data from replacing another school's view.

The last-usable-owner safeguard was already present in the current working tree. It was inspected and retained: membership changes, global account status changes and recovery share the existing locking/transaction rules. The full backend and browser suites exercise owner removal/suspension conflicts and auditable platform recovery. No owner privileges are silently granted at startup.

## Deployment and operation

No environment, dependency or lockfile changes were made for this implementation. No Atlas connection, real data import, migration apply or destructive database action was performed. Tests use disposable local replica sets; browser tests run on separate test ports with fixture accounts.

This extension adds optional fields and explicit catalog provisioning, so it introduces no new migration command or automatic backfill. A deployment must already have the existing school setup v1/onboarding v2 schema and grants. If those are missing, use the previously documented `migrate-school-onboarding.ts --preflight` and deliberate maintenance-time `--apply` procedure with backups; neither was run against your configured database. Existing custom roles need deliberately assigned view/manage grants for the desired features.

For local live mode, keep the backend running with `yarn dev`, then launch the frontend with `VITE_APP_MODE=live npm run dev`. Existing `.env` files were preserved, so a file that still selects demo remains demo unless overridden. Vite uses port 5173 with strict-port behavior; the backend origin allowlist must match the browser origin exactly. Live production builds must explicitly set `VITE_APP_MODE=live` and a public deployment API URL. Backend auth still requires its existing JWT configuration, MongoDB replica-set connectivity and appropriate cookie/origin settings.

Do not use demo localStorage as live data or import fictitious fixtures into a real school. Configure General, select an academic year, configure classes/sections, review subjects, then import staff/students. Academic imports are bounded to 1,000 rows and 1 MiB input; bulk structure to 200 changed rows with bounded snapshots. For larger schools/imports, operational load testing, batch planning and retention controls remain necessary.

## Remaining limits

This completes the settings, academic foundation and people-onboarding integration described above. It does not implement attendance, finance/fee collection, payroll/salary history, exams/results, timetable, messaging delivery, document storage or annual promotions/transfers. Those existing demo modules remain demo-only and unavailable as live operational data. Staff departments/designations currently use validated profile text rather than a live department/hierarchy administration module. A full employee payroll/profile lifecycle needs its own permissions and history design.

Import execution remains the existing process worker with durable MongoDB leases. Multi-process throughput, import retention/cleanup, monitoring, disaster recovery, production Atlas deployment, privacy/compliance assessment and an independent security review were not verified. Large lists/images still need realistic load measurements. Passing isolated tests does not establish production security or production readiness for the entire SaaS.
