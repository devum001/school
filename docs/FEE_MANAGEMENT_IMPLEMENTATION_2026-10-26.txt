HOW TO ENABLE AND REVIEW
1. In the backend repository, stop the existing development server, then run:
   ./node_modules/.bin/ts-node commands/initialize-school-fees.ts --preflight
   ./node_modules/.bin/ts-node commands/initialize-school-fees.ts --apply
   yarn dev
   These commands have NOT been run against your configured database. They add
   four fee collections and indexes and grant the five fee permissions to protected
   owner roles in active schools. They preserve existing records/indexes and leave
   custom roles unchanged. A MongoDB replica set is required for transactions.
2. Start the frontend in live mode with your existing API URL:
   VITE_APP_MODE=live npm run dev
   PowerShell equivalent: $env:VITE_APP_MODE="live"; npm run dev
3. Sign out/in as the school owner. Open Finance > Student Fees.
4. Select the academic year, class and optional section; choose Fee setup pending.
   Select students (including all matching pages) > Set up fees. Enter common fees,
   concessions/scholarships and a due date. Single balance is the default; choose
   Split into installments only when needed. Review individual amounts and save. Saves progress in batches of 25.
5. Select students > Previous-year dues. Enter one previous period and outstanding
   balances. Historical opening paid belongs inside current-year fee setup, while
   old outstanding debt belongs here. Neither is counted as today's cash collection.
6. Manage Fees opens the student's ledger across years. Collect payment supports
   partial payments, oldest-due allocation or custom installment allocation. Confirm
   to issue a downloadable/printable receipt. Transactions lists recorded payments.
7. Authorized users can reverse an incorrect payment with an optional note or correct old
   opening debt. Original receipts/history remain. Paid allocations cannot be
   silently deleted or reduced. Students with fee accounts cannot be hard-deleted.
8. Test the existing Students Excel import: preview > confirm once > progress >
   View Enrolled Students. Lost confirmation responses are reconciled with job state.
   No extra Excel workbook is required for fees.

FUNCTIONAL SCOPE
- Existing Finance shell/navigation/styles and shared document renderer are reused.
  Demo retains its local repository and original Finance screens. Live uses APIs.
- Dashboard: net current-year fees, concessions, setup-pending count, outstanding,
  overdue, current-calendar-month collections and class balances. Filters constrain
  the student population; status narrows the directory, not the summary cards.
- Per-student integer-paise agreements, exact installment totals, discounts and
  scholarships with optional notes, opening paid balances, prior-period debts and history.
- Current-year paid includes historical opening paid; Transactions contains actual
  recorded payments only. Transaction year selection filters by payment date.
- Former/no-active-enrollment students can carry and pay old dues without inventing
  a new enrollment. Existing accounts prevent overlapping opening balances.
- Server pagination (50), debounced search, bounded writes (25), individual schedule editor,
  paginated bulk review, CSV export of the displayed page and mobile ledger layout.
- Fee permissions: fees.view, fees.manage, fees.approve, fees.collect, fees.reverse.
  Approval is required for concessions/scholarships and reductions of existing dues.
  Tenant checks, fresh authorization, CSRF and audited transactions remain enforced.
- Fee payments and setup use idempotency keys. After a lost save response, the client
  checks operation status; uncertain retries retain the same key. Amounts and names
  are not stored in the retry-key storage. Stale edits and overpayments are rejected.

API DEPENDENCIES (under /api/v1/schools/:schoolId/fees)
GET /context; GET /; GET /students/:id; GET /payments; GET /operations/:key
POST /agreements; POST /opening; POST /payments; POST /payments/:id/reverse;
POST /accounts/:id/correct-opening
New collections: student_fee_accounts, student_fee_payments, student_fee_operations,
student_fee_counters. The initialization command adds storage and permissions without rewriting existing student data.
Fee routes return a clear initialization-required response until storage is ready.

PERFORMANCE WORK
- Import validation and commit operate in bounded transactions with transaction-local
  class/section/student/enrollment maps. Duplicate roll checks use a linear scan.
- Progress writes touch only processed rows instead of validating/saving the whole
  embedded import repeatedly. Successful profiles, enrollments and progress commit
  together. Row conflicts are isolated; cancellation/revocation remain checked.
- Repeated confirmation of the same import returns its saved status, not a conflict.
- Completed polling invalidates cached lists; uncertain mutations invalidate reads.
  No generic automatic POST retry was introduced.
- Independent school access reads run concurrently outside transactions. Transaction
  operations remain sequential and authorization is not cached across requests.
- Finance is lazy-loaded; the measured live-router chunk fell from about 958 kB to 663 kB
  after splitting this work. The existing >500kB chunk warning remains.

REMAINING LIMITS / MANUAL ACTIONS
- Run the additive fee initializer, then sign in again. Grant custom fee roles only
 the permissions they need. Existing suspended-school owner roles are not updated.
- Current receipts use the shared Classic renderer and live school logo/accent;
 live template/letterhead customization is not introduced by this change.
- Fee setup is an overall per-student agreement; separate transport/tuition fee-head
 accounting, online payment gateway, bank reconciliation and refunds are not added.
 A reversal corrects a recorded payment; it does not transfer money back to a bank.
- Bulk setup targets unconfigured students; existing agreements are edited separately
 to protect paid installment allocations. Export is explicitly the displayed page.
- Last 20 agreement changes are shown in the ledger; complete operation/audit records
 remain in MongoDB. Receipt listing is cursor-paginated. No destructive history trim.
- Initialization-script behavior was reviewed; real-database preflight/apply is a
 manual deployment step and has not been claimed as tested on Atlas.
