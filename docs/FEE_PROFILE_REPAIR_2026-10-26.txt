FEE FLOW
1. Finance > Student Fees > select year/class/section > select students > Set up fees.
2. Enter the common fee, optional concession/scholarship and optional note.
   Single balance is the default. Split into installments reveals count/interval.
3. Review students, adjust individual amounts and Payment details, then Save fee setup.
   Previously received money can be entered as Already paid, with its recorded-on date.
4. Open a student ledger as a page. Collect payment opens one dialog with the amount,
   payment method/date and the allocation visible together. There is no stacked ledger
   dialog and no additional payment-review dialog.
5. Payments apply to the earliest unpaid balance across years, even before its due date.
   Example: 3,000 due 30 October and 5,000 due 30 November; receive 4,000 on 28 October:
   3,000 clears October and 1,000 goes toward November. Older unpaid debt is cleared first.
   Choose specific installments remains available for an agreed alternative allocation.
6. A single-balance agreement still accepts partial payments. Overpayments are rejected.
   Schedule totals must equal the final fee: this financial consistency check remains.
7. Notes are optional for concessions, changes, corrections and payment reversals.
   Permission checks, audit records, revision checks and paid-allocation protection remain.
8. Fee forms use the shared loader; form errors appear beside the bottom actions.
   Class filters use the shared natural class order (1, 2, ... 10, 11, 12), including
   Class/Grade prefixes and ordinal suffixes. Section selection resets when class changes.

STUDENT PROFILE
The original demo StudentProfilePage, StudentAttendance, StudentAcademics and
EntityDocuments presentation is reused in live mode. Overview, Attendance, Fees,
Progress Report and Documents use real student-specific backend records.
- Student identity, guardian, academic year and enrollment come from MongoDB.
- Attendance calendar and overview percentages agree; unmarked days are counted
  separately and are not treated as recorded absences. Other attendance screens and
  their existing calculation rules were not changed.
- Academic results use existing exams and marks with assignment/subject filtering.
- Fees reuse the same live ledger and receipts as Finance. Changes refresh profile totals.
- Edit uses the existing full live student form. Delete uses the existing protected API;
  students with financial history remain protected from hard deletion.
- Document metadata loads only when Documents is opened. File content loads only when
  viewed/downloaded. PDF/PNG/JPEG/WebP uploads retain the demo's 2 MiB limit, with byte
  signature/size checks, tenant checks, CSRF, audits and duplicate-upload protection.
- Users without attendance/academic/fee access do not receive those protected records.
  Unlinked teaching permissions do not prevent basic student-profile viewing.
- Demo still uses the existing local repository. Live never substitutes demo records.
- The obsolete reduced live profile was removed in favor of the original profile UI.
- Parent messaging is not connected by this task. The profile identifies it as unavailable
  instead of sending a live user into an unsupported notification workflow.

MANUAL DATABASE SETUP
Run once in the backend repository before uploading student documents:
  ./node_modules/.bin/ts-node commands/initialize-student-documents.ts --preflight
  ./node_modules/.bin/ts-node commands/initialize-student-documents.ts --apply
Then restart the backend and frontend.
This is additive: it creates student_documents and its indexes; it does not rewrite
or delete existing school/student/fee records. These commands have NOT been run
against your configured database. Transactions require the existing replica-set setup.
If fees were never initialized, the existing initialize-school-fees.ts preflight/apply
from the preceding fee implementation is still needed; it was not changed here.

LIMITS / REMAINING ITEMS
- Real Atlas data, real school accounts, production network latency and real document
  initialization were not tested or modified. All database tests used disposable local data.
- Student documents are stored in MongoDB with a 2 MiB per-file limit. Object-storage
  offloading/virus scanning is not included in this change; signature checks are not a
  malware scan. Existing demo file formats and limits were preserved.
- Parent notification workspace remains a separate integration dependency. Existing
  manual report preview/download and WhatsApp handoff are retained where applicable.
- Academic marks edits continue through the existing class results workflow.
- Optional notes do not bypass concession approval, audit recording, exact fee totals,
  stale-edit protection or fee-history retention.
