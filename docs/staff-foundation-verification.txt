Staff attendance, staff profiles, assignments, Quick Connect and permissions
Verification report — 31 October 2026

IMPLEMENTED
- Initial school-account access preserved. New schools still receive all school permissions. No existing owner was demoted. Stored permissions remain authoritative; owner status is not a general permission bypass.
- School attendance rollout date, school-local finalization cutoff, and individual staff activation date. Active linked accounts are required for activation. Application sign-in never records attendance. No automatic absence before school rollout/staff activation. Exempt/manual staff, leave and non-working days are handled separately.
- Shared attendance calculation supplies register, staff directory, profile calendar and Quick Connect. Missing punch-in becomes provisional before cutoff and Absent after cutoff. An absence correction request preserves Absent while pending; no automatic salary or leave deduction is introduced.
- Staff directory search by name/employee code/phone, daily attendance filters, profile links and permission-specific actions. Class/section controls belong to Staff assignments.
- Assignment search and class/section/subject filters; revision-checked replacement and atomic batch assignment. Previous assignments are archived with audit events, preserving records. Student roster, contact, profile and document reads now check stored teacher assignment scope.
- Staff profiles reuse existing panels, navigation, attendance calendar, salary setup, payslips, leave review and account creation. Real Overview, Attendance, Assignments, Leave, Salary and Account tabs appear according to permission/data availability. No Daily Records tab. Mobile header wraps contact/actions.
- Actual student guardian phone and click-to-dial contact links. Quick Connect sidebar with Students, Teachers and Other Staff, scoped live data, search, attendance filters, 50-row paging and loading/error/empty states. Demo uses existing local data; there is no live-to-demo fallback. Invalid/placeholder phone values are not made dialable.
- Grouped permission modules within existing View/Manage tabs, configurable role suggestions, sensitive delegation confirmation. New separate staff create/edit/archive, attendance view, leave approve/reject and contact-directory grants. Legacy staff.manage/attendance.manage remain umbrella grants for compatibility.

HOW TO CHECK LOCALLY
1. Restart the backend and frontend using their existing development commands; keep frontend in live mode for API testing. No environment values were changed.
2. Sign in as the initial school account. Open School settings > Staff & Payroll > Work & Leave. Choose the school attendance tracking start date and finalization time (school local time).
3. Open a teacher/staff profile. Create/link the school login first, then Set attendance start to today or a later date. Activation cannot be silently backdated; a started boundary cannot be moved through this action. Joining date alone does not enable automatic absence.
4. Check the staff attendance register and teacher profile. After cutoff, a scheduled, active, activated punching staff member with no punch is Absent. Before activation, missing records are Unmarked. Leave/off/holiday records are not counted as absences. An ARS can correct an eligible finalized absence.
5. Use Staff assignments from Teachers/Staff to add or replace assignments. Confirm the replacement; the old teacher loses that assignment's student access on the next API read. Independent class-teacher designations or other remaining valid assignments continue to grant their own access.
6. Open Quick Connect, switch tabs, search by phone and follow profile/call links. Calling opens a dialer; it does not place a call automatically.
7. In Roles & Permissions, create a staff role and explicitly grant the required View/Manage permissions. Quick Connect requires contacts.students.view plus students.view or teaching.self, or contacts.staff.view plus staff.view. Existing owners with the corresponding person-view grant retain contact access. Custom roles are not automatically broadened to the contact directory.
8. Test demo separately using the existing demo mode command. Its data remains independent.

LIMITS / FOLLOW-UP WORK
- Missing-day absences are calculated on read, not written by a scheduled finalization job. Actual stored attendance/corrections remain intact. Changes to current work rules/account state can affect historical derived missing days; immutable policy-version/day snapshots are not implemented. Historical automatic absence is deliberately bounded by rollout and activation dates.
- The contact directory batches reads (no per-person database loop), caps matching records at 10,000 and returns 50 per page. Attendance filtering/counting is performed over the bounded result set, not fully database-paginated. The existing monthly HR workspace still has its 500-staff limit. Larger-scale load testing and immutable attendance aggregation need separate work; no production latency guarantee is made.
- Assignment eligibility uses existing active teaching-staff, academic structure and duplicate/conflict rules. There is no qualification matrix or timetable clash model in the existing application; these rules were not invented. Archived assignments/audit history are preserved; the assignment UI focuses on current allocations rather than introducing a new history viewer.
- Existing manage permissions for some modules (including student/import/setup workflows) still group several operations. Staff actions and leave decisions were split in this work; not every action throughout the portal now has an independent grant. Existing account/role and payroll permissions remain separate.
- Server authorization resolves current grants/assignments on requests; no push mechanism closes a page already displayed in another browser when an administrator changes access. Contact/student profile reads avoid stale cached authorization-dependent data. Previously downloaded information cannot be recalled.
- Automated browser coverage verifies representative flows, not every screen/action combination in the portal. Only the new targeted demo/live browser tests were run, not the entire existing Playwright suite. Database regression tests exercised disposable MongoDB, not the deployed environment.
