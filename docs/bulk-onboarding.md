# Bulk school onboarding

This phase extends the existing live school workspace. Demo mode keeps its own localStorage data and never supplies fallback data to live mode. The school owner lands on the first incomplete required step they can manage; saved progress comes from the backend. A school with essential setup complete opens its review/dashboard and may import people later.

## Owner workflow

1. Save essential school information, then create an academic year and explicitly make it current.
2. Select offered grades from Nursery, LKG, UKG and Classes 1–12; rename or add custom grades. Review and save one batch.
3. Select classes, apply a section pattern, then adjust each class’s sections. Review and save together.
4. Copy suggested subjects for selected grades, rename/add/archive and mark optional subjects. Suggestions are a starting point, not a board-certified syllabus. Senior streams are chosen by the school.
5. Open Staff or Students. Download a CSV/XLSX template, choose the year and matching mode, upload, wait for validation, correct rows and confirm. Import history survives refresh/logout and is visible only to authorized administrators of the same school.
6. View the directory and annual enrollments. Assign active teaching staff to existing class/section/subject combinations. Withdraw enrollments or end assignments explicitly when necessary; historical records remain.
7. Review actual saved counts and return to optional tasks later. Staff identities, student identities and teaching assignments do not make essential setup mandatory.

All academic edits have explicit review. Omitted rows are never implicitly deleted. Referenced academic records cannot be archived while active enrollments/assignments use them. Read-only roles see data without mutation controls. School switches and API errors do not fall back to another school or demo data.

## Relationships and indexes

The existing `schools`, `academic_years`, `academic_classes`, `academic_sections`, `academic_subjects`, authentication, membership, role/grant and audit collections remain. Every operational child has `schoolId`; academic structure and operational relationships additionally have `academicYearId`.

| Collection             | Identity and ownership                                                                                     | Important indexes / purpose                                                                                                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `academic_classes`     | School/year class, normalized name; revision and active/archived status                                    | Existing unique school/year/name key and school/year pagination indexes.                                                                                                                                                                        |
| `academic_sections`    | School/year/class section                                                                                  | Existing unique school/year/class/name key; parent-scoped pagination.                                                                                                                                                                           |
| `academic_subjects`    | School/year/class subject, now also `optional`                                                             | Same parent-scoped uniqueness; IDs survive edits/archive. Missing optional on older records reads as false.                                                                                                                                     |
| `staff_profiles`       | School-local staff code, profile independent of a login; optional reserved `userId` relation               | Unique `(schoolId, codeKey)` prevents duplicate staff. `(schoolId, _id)` supports cursor lists. No account is created or linked by import.                                                                                                      |
| `student_identities`   | School-local permanent admission number; name, birth date and optional guardian/contact/address            | Unique `(schoolId, codeKey)`; `(schoolId, _id)` pagination. Siblings/shared contacts are not deduplicated by name or phone.                                                                                                                     |
| `student_enrollments`  | School/year/student → class and section; optional roll; active/withdrawn                                   | Unique `(schoolId, academicYearId, studentId)`; partial unique `(schoolId, academicYearId, sectionId, rollNumber)` for numeric rolls. Withdrawn rolls remain reserved as historical identities. Year cursor and class/status reference indexes. |
| `teaching_assignments` | School/year/staff → class, section and subject; active/archived                                            | Unique `(schoolId, academicYearId, staffId, sectionId, subjectId)`; year cursor and class/status indexes. Reassigning an archived tuple restores the same record.                                                                               |
| `roster_imports`       | School/year, kind, matching mode, actor, state, fingerprint, bounded embedded row results and worker lease | Unique `(schoolId, fingerprint)`; `(schoolId, kind, _id)` history cursor; `(status, leaseUntil, _id)` claim/recovery.                                                                                                                           |
| `schema_upgrades`      | Deployment initialization ledger                                                                           | Existing unique version key. A marker means the versioned migration finished, not that a school has completed setup. Do not manually set or delete markers to bypass checks.                                                                    |

Profiles are not annual enrollments. A later-year import can create another enrollment for the same student without duplicating their identity. Imports reject transfers, roll changes or reactivation of an existing enrollment. Withdrawals are explicit and preserved; a full transfer/promotion/reinstatement workflow is outside this phase. Closing a year prevents changes to its structure and relationships. Closed-year relationships remain historical and do not block archiving a person’s current profile; active relationships in open years do.

The catalog lives in backend `src/catalogs/indiaSchool.ts`, version `india-general-2026-v1`. It is packaged immutable suggestion data, not a shared writable subject collection. Copying suggestions creates ordinary school-owned records. Updating the catalog never changes saved school subjects. Names use NFKC normalization, whitespace folding and case folding for uniqueness; display names remain editable.

## API contract

Existing response envelopes, cookie JWT authentication, CSRF protection, request IDs and sanitized errors are reused. Paths below are relative to `/api/v1/schools/:schoolId`. IDs are validated and resolved within the active tenant/year; matching names alone never establish enrollment authority.

| Method / path                                                            | Request / behavior                                                                                                                                                                                                |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/setup/catalog`                                                     | Active school member; returns versioned grade and subject suggestions.                                                                                                                                            |
| GET `/academic-years/:yearId/structure?kind=classes\|sections\|subjects` | Required structure/year view permissions. Returns year, up to 200 classes and 2,000 children plus `truncated`; bulk UI disables saving if incomplete.                                                             |
| POST `/academic-years/:yearId/structure-batch`                           | `{kind, rows:[{id?, revision?, classId?, name, grade?, status, optional?}]}`; corresponding manage permission. 1–200 explicit changes, one atomic transaction. Existing edits require revision.                   |
| GET `/people/staff` or `/people/students`                                | Corresponding view permission; `after` cursor and optional `search` (name/code, at most 80 chars); 50-row pages.                                                                                                  |
| PATCH `/people/:kind/:id`                                                | `{revision,status}`; manage permission; active/archived only, reference protection, audit.                                                                                                                        |
| GET `/academic-years/:yearId/enrollments`                                | `students.view`; paginated enriched rows and year context, including student code/name, class, section, roll, status and revision.                                                                                |
| GET `/academic-years/:yearId/teaching-assignments`                       | `assignments.view`; same pagination/year context, staff/class/section/subject labels.                                                                                                                             |
| POST `/academic-years/:yearId/teaching-assignments`                      | `assignments.manage`; `{staffId,classId,sectionId,subjectId}`; active teaching staff and active matching references required.                                                                                     |
| POST `/academic-years/:yearId/enrollments/:id/end`                       | `students.manage`; `{revision}`; explicitly withdraw; does not delete student identity.                                                                                                                           |
| POST `/academic-years/:yearId/teaching-assignments/:id/end`              | `assignments.manage`; `{revision}`; archive assignment.                                                                                                                                                           |
| POST `/imports`                                                          | `{kind:'staff'\|'students', academicYearId, mode:'create'\|'update', grid:string[][]}`; corresponding manage permission; returns durable job summary, initially validating.                                       |
| GET `/imports?kind=staff\|students&after=…`                              | Manage permission for that roster; 50 summaries per page.                                                                                                                                                         |
| GET `/imports/:id?offset=0`                                              | Summary plus columns and up to 50 row previews/results; `nextOffset` for subsequent pages.                                                                                                                        |
| PATCH `/imports/:id/rows`                                                | `{revision,number,cells}`; draft/pending rows only; returns job to validation. Original spreadsheet row numbers are retained.                                                                                     |
| POST `/imports/:id/confirm`                                              | `{revision}`; only a fully validated draft with no row errors can queue.                                                                                                                                          |
| POST `/imports/:id/cancel`                                               | `{revision}`; cancel remaining work; committed rows remain.                                                                                                                                                       |
| POST `/imports/:id/retry`                                                | `{revision}`; paused/cancelled/completed job; revalidate pending/failed rows, preserve successes, then require confirmation again.                                                                                |
| GET `/imports/:id/results`                                               | `{csv}` containing original columns, row number, outcome and safe validation errors; formula prefixes escaped. Results include Row/Outcome/Errors; copy the original template columns when preparing a re-upload. |
| GET `/onboarding`                                                        | Existing endpoint now reports distinct classes/sections/subjects required steps, optional staff/student steps and actual counts.                                                                                  |

New explicit permissions: `staff.view`, `staff.manage`, `students.view`, `students.manage`, `assignments.view`, `assignments.manage`. Owner roles receive these at initialization. Custom roles remain unchanged; grant only intended access in Roles. Presets include view dependencies for useful workflows. Manage grants do not bypass tenant membership, active global account/school/membership checks or CSRF. Platform Super Admin access does not implicitly grant school operations access.

Last-usable-owner protection and audited recovery were already implemented in the preceding phase and remain in use. Global disable and membership/ownership changes serialize on existing locks; concurrent attempts cannot remove all usable owners. Existing regression tests are retained.

## Import strategy and operational limits

- Browser parses UTF-8 CSV or XLSX into a bounded grid. Server independently validates dimensions, exact supported headers, strings, fields, duplicate codes/rolls and every reference. Binary files are not stored.
- Limit: 1,000 data rows, 1 MiB file/canonical grid, 300 characters per cell with tighter field limits. Parser rejects XLSX formulas/errors and excessive ZIP expansion. Excel identifiers must be text to retain leading zeros. Dates use YYYY-MM-DD; Excel date serials are supported for Birth Date and Joined On.
- Required staff fields: Staff Code, Staff Name, Teaching (Yes/No). Required student fields: Admission Number, Student Name, Class, Section. Optional profile/contact fields can be blank. No generated credentials or guessed person matching.
- Default `create`: matching normalized code plus identical profile/enrollment skips; different details fail validation. Explicit `update`: replace matching profile fields (blank optional fields clear them), with an optimistic revision captured at preview. New codes can still create records. Adding a new-year enrollment to an existing identity is reported as updated.
- Fingerprint hashes normalized parsed cells, kind, year and mode within the school. Re-uploading that file returns its existing job, even after an administrator corrects its preview; it does not undo those corrections. A different file still matches people by permanent code. Repeated codes/rolls inside a file are errors, not silent last-row wins.
- Academic batches are all-or-nothing. Roster **processing is partial success by row**, stated before confirmation. Each profile/enrollment and its job outcome/progress commit in one transaction. A later conflict fails that row without rolling back earlier successes. Results always distinguish created/updated/skipped/failed/pending.
- Worker states: validating → draft → queued → processing → completed. Paused and cancelled jobs are resumable. A 30-second lease, 25-row work batches, periodic authorization checks and transactional writes allow safe process restart/multiple workers. Expired leases can be reclaimed; the lease token prevents a previous worker from committing after another takes over. Shutdown stops claiming jobs and awaits the current bounded batch before disconnecting MongoDB.
- Changing permissions, disabling access, closing the year or unexpected failures pauses work with a sanitized message. Correct the condition and revalidate remaining rows. Saved successes are kept. Up to ten unfinished jobs per school prevents unbounded queued previews.
- Import rows contain personal information. Access is restricted to roster managers; logs and audit events do not dump file contents. There is no automatic retention deletion in this phase: production operators must define retention/access/backup policy. No background cleanup silently discards results.
- Bounded embedded rows simplify durable atomic outcomes at this scale. This implementation has not been production load-tested. Very large schools should split files; a separate row collection/worker service can be introduced before increasing these limits.

## Deployment and configuration

No real database was connected or migrated by this implementation. No credentials, environment files, dependencies or lockfiles were changed.

Deploy backend/frontend together during maintenance. Keep a database backup. In the backend repository run the explicit initializer against the intended configured replica set:

```sh
./node_modules/.bin/ts-node commands/migrate-school-onboarding.ts --preflight
./node_modules/.bin/ts-node commands/migrate-school-onboarding.ts --apply
```

Preflight is read-only. Apply incorporates the existing setup-v1 migration, creates the new indexes, grants the six new capabilities to built-in Owner roles only, records audit events and writes `school-onboarding-v2` after success. It does not seed students/staff, invent credentials, delete collections or rewrite custom roles. Re-running is idempotent. Both an empty database and an existing foundation require this explicit initialization; startup fails clearly if it is missing. Do not drop existing tables/collections to fix that message.

Then restart the backend and frontend, sign in as a school owner, and open School setup. Existing JWT/MongoDB configuration remains required; live frontend uses its configured API URL. The durable worker starts only with MongoDB and auth enabled. Demo mode remains selectable through the existing Vite configuration and needs a Vite restart when changing environment mode.
