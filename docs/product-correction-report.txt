School product correction — implementation and verification
20 October 2026

Status
This report records the completed repair slices and the remaining product work. It is
not a claim that every final acceptance item in the master request is finished. The
original demo Overview, Academics, attendance register and class cards now have live
adapters. The existing staff/payroll implementation is retained and extended.

Investigation / punch error
Read docs/product-correction-investigation.txt for the initial code-path report supplied
before broad edits. An isolated MongoDB/API test reproduced the old HR_PUNCH response
for an active linked teacher whose employment policy had never been configured. No
configured Atlas record was inspected, so the exact failing condition in the user's
real teacher record has not been verified.
New teaching profiles with no saved employment policy can punch before salary setup.
An explicitly saved none/manual policy or a future effective policy still controls
eligibility. Punch may be selected before creating the login; login and school/staff
linking remain mandatory when actually punching. School working days, holidays,
employment dates, approved leave, geofence/accuracy/freshness, payroll locks, reviewed
records and punch sequence remain enforced. The self-service response exposes the
actual eligibility reason and next action; disabled buttons explain missing setup.
Distinct fixed error codes cover missing campus, disabled mode, dates, weekly off,
approved leave, already in, not in, completed day and reviewed day. An earlier open,
unreviewed day blocks a new session. Retry keys are retained on client failure. Server
Date supplies both event time and its school-timezone work-date context. No browser
punch timestamp is trusted. Duplicate retries return the existing event without a
second punch, and invalid requests do not create events.

Shared presentation and data boundaries
- Original DashboardPage/AttendanceTrend: layout/cards/chart/donut/class pulse/absent
  student table retained. Persisted student attendance drives the figures; empty real
  schools remain empty. Missing notification delivery is explicitly identified.
- Original AcademicsPage/TestDialog/MarksDialog/ResultsView/TestResult: existing tests,
  configured subject choices, section/whole-class scopes, marks import/preview,
  maximums, absent A, pending cells, rankings and exports are reused. Live writes use
  authenticated APIs, revision checks and transactions. Both client and server enforce
  the demo's rule that marked students or subjects cannot be removed by editing a test;
  the user must clear marks explicitly first. Blank subjects are omitted exactly as in
  the original marks-sheet workflow. No replacement curriculum is introduced.
- Original AttendancePage/ClassFilters/ClassesPage: school/date/class/section context
  and status controls are reused, including sectionless classes. Assigned users cannot
  follow links into the school-wide private student profile area without permission.
- SchoolFeatureContext is a typed boundary for live state and asynchronous writes;
  the demo still uses its existing repository. The previous repository implementation
  moved intact to demoRepository.ts, behind repository.ts's mode-aware lazy loader.
  This removes eager demo seeds/persistence from live imports and rejects accidental
  demo writes in live mode. Sample logos, signatures and other artwork are also loaded
  only in demo; live branding never falls back to a sample school's artwork.
- The shared class-settings grid now allows its table to scroll inside the available
  width instead of expanding the whole mobile page. Layout/navigation are retained.
- Lazy loading separates Overview, Academics, attendance and class bundles.

Teacher assignments and privacy
New capabilities distinguish school-wide access from assignment-scoped access:
overview.view; teaching.self; student-attendance.view/manage;
student-attendance.assigned; academics.view/manage; academics.assigned.view/manage.
There are now 36 explicit school capabilities (the earlier catalogue had 27).
Every learning API checks active school membership and current server assignments.
Teaching assignments grant their class/section/subject; class-teacher designation
provides the designated section's broader class responsibility. Ending an assignment
revokes its protected data and writes on the next request, including forged direct
requests. Learning reads bypass retained response caching to prevent stale authority.
Teacher-scoped responses omit private guardian/contact data and all payroll data.
Write scopes are rechecked inside the existing school authorization transaction.
Sectionless teaching assignments are supported by the existing assignment entity.

HR and permissions
Teacher self-service has Attendance, Leave, Salary and My profile sections. The monthly
calendar retains existing statuses, readable legends, selected-day details and school-
timezone punch times, with previous/next month navigation. Future days are not absences.
The teacher receives only their own HR records. The own-HR sidebar link is shown only
when an active staff identity is actually linked. School administrators can open an
individual calendar from the attendance register, filter by member/department/date and
see present, late, explicitly reviewed absent, active punch, review and pending-leave
counts. Missing attendance is not automatically made absent or unpaid.
Pending leave can be cancelled by its own linked staff member before it starts; history
is retained. Approved/rejected requests cannot be cancelled through that action. New
requests and approval decisions appear in the appropriate leave month; leave approval
feeds the same approved-date snapshot used by the attendance calendar and payroll.
Existing salary versions, approval locks, partial payments, balances and audit checks
remain. Teachers and non-teaching staff remain separated in teacher HR tabs.
Role descriptions and affected-member counts were added. The existing View/Manage
editor now includes assigned-class capabilities and read dependencies. Assigned roles
cannot be deleted; protected owner roles and last-usable-owner transaction checks remain.
Owners see the original complete settings tab and nested-section structure. Unsupported
live sections are identified explicitly and never read or write demo persistence.

API additions
GET /schools/:schoolId/academic-years/:yearId/learning
  area=overview|classes|attendance|academics; optional date=YYYY-MM-DD
POST /.../learning/exams
PUT /.../learning/exams/:id
DELETE /.../learning/exams/:id (revision)
PUT /.../learning/exams/:id/marks (revision, changed sheets)
PUT /.../learning/attendance (date, classId, sectionId, rows and revisions)
POST /schools/:schoolId/hr/leave/:id/cancel (revision)
Existing onboarding status adds selfLinked. Existing roles add description/memberCount.
All writes retain authentication, CSRF, school isolation and audit controls. Generic
errors remain sanitized; only allowlisted domain messages cross the API boundary.
Exam creation has a school/year-scoped idempotency key; replays must match the complete
validated class/section/subject selection. A stale roster or revision rejects a write.
Student deletion also clears its new attendance/results records. Moving an enrollment
with learning history and deleting structure referenced by tests is guarded.

Manual deployment step — NOT RUN on the configured database
From the backend directory, first review:
./node_modules/.bin/ts-node commands/initialize-school-learning.ts --preflight
Then, during the intended deployment/maintenance window:
./node_modules/.bin/ts-node commands/initialize-school-learning.ts --apply
This installs the three learning collections and declared indexes, verifies no duplicate
school/user-to-staff links, creates the unique link index and explicitly grants the nine
new capabilities to protected owners of active schools, with audit records. Custom roles
are unchanged. The script is repeatable and does not drop data/indexes. No seed data or
credentials are created. Until installation, learning endpoints return LEARNING_NOT_READY
instead of creating storage silently. Other school settings continue to work. Restart
the backend/frontend after deploying code. Configure a campus in Staff & Payroll →
Work & Leave and verify the teacher's joining date and selected attendance method.
Existing owners need this explicit new-capability grant; no startup privilege backfill
runs. Newly provisioned school owners receive the current full permission set.

Preservation / operational limits
Both working trees contained extensive prior changes. No git reset/clean/commit or
user environment edits were performed. Initial blanket copying was rejected by automatic
approval review; exact git-apply patches were then conflict-checked and applied only
with matching SHA-256 baselines and byte-for-byte file backups under /tmp. Only the
reviewed source/test/command paths changed in the backend. Production build output is
regenerated, ignored output. Configured Atlas connections, school records, migrations
and seeding were not run. Database/browser tests use isolated local replica sets.
The geofence checks browser-provided location; device attestation/anti-spoofing is not
provided. There is no claim of a real-school load test or production database test.
Learning snapshots are bounded (200 classes, 1,000 sections, 10,000 enrolled students,
500 staff, 1,000 exams and bounded attendance/results); exceeding a bound fails clearly
instead of silently truncating data. Larger-school pagination/aggregation remains work.

Remaining master-request dependencies
- The full student-fee/receipt/finance workflows are not implemented as live APIs.
  The pre-existing live Finance route still represents payroll, rather than all original
  finance tabs. This needs its own complete financial vertical slice.
- Notification delivery, communication/template settings, regional preferences and
  some data/security settings still require live persistence/integration. Their original
  owner settings locations remain visible; unsupported sections explain the dependency.
- Student-directory/profile presentation is the existing earlier live implementation;
  it has not been fully replaced by the original demo profile with every module tab.
- Staff bulk imports retain preview/correction/profile persistence, but do not bulk
  provision credential invitations or salaries. Login remains an explicit school-owned
  per-staff action; existing global accounts require authorized membership/linking.
- Department/designation settings do not yet reproduce every nested demo designation
  operation. Full visual/workflow parity for all staff-profile fields still needs review.
These are not marked complete, and unsupported operations do not silently use demo data.
